The module is a Kotlin/JVM Gradle application (`build.gradle.kts`) implementing the application service layer of the accounting subsystem. It defines two use-case interfaces — `AccountingUseCase` (order payment, completion, refund, settlement) and `SettlementUseCase` (confirm, mark paid) — with concrete implementations `AccountingApplicationService` and `SettlementApplicationService`. Command objects in `command/` (`RecordOrderPaidCMD`, `RecordOrderCompletedCMD`, `RecordOrderRefundApprovedCMD`, `RecordSettlementPaidCMD`) carry input data for each use case. Event adapters in `AccountingEventHandler` implement `IntegrationMessageHandler` for external commerce events (`PaymentCapturedIntegrationEvent`, `OrderCompletedIntegrationEvent`, `PaymentRefundSucceededIntegrationEvent`) and `DomainEventListener` for internal `SettlementPaidEvent`, delegating to the use cases. Dependency direction is strictly inward: application services depend on domain repositories (`JournalEntryRepository`, `LedgerAccountRepository`, `AccountingPeriodRepository`, `SettlementStatementRepository`) and common framework abstractions (`Result`, `BusinessError`, `DomainEventPublisher`, `IntegrationMessageHandler`), never on infrastructure or other application modules. Tests under `src/test/kotlin` use in-memory fakes (`FakeJournalEntryRepository`, `FakeLedgerAccountRepository`, `FakeAccountingPeriodRepository`) to exercise the same use-case APIs.
