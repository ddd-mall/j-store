The module implements the application layer of a DDD order service. `OrderUseCases.kt` declares two stable inbound-port interfaces — `OrderUseCase` and `AfterSaleUseCase` — which are implemented by `OrderService` and `AfterSaleApplicationService`. Each use case follows a uniform orchestration pattern: load the aggregate via a repository, invoke domain behavior on the aggregate, persist with `repository.save`, then publish pending domain events via `publishPendingEvents(domainEventPublisher)`. Cross-cutting concerns such as idempotency (SHA-256 hashed receipts stored through `AfterSaleCommandReceipt`) and allocation actions (`AllocationAction.APPROVE`/`RELEASE`) are handled inside `AfterSaleApplicationService` before delegating to the domain. Integration boundaries are expressed as thin `IntegrationMessageHandler<T>` implementations in `CommerceIntegrationMessageHandlers.kt`, `OrderStockEventHandler.kt`, and `OrderStockInsufficientEventHandler.kt`, each mapping an external contract event from `j-store-integration-contracts` into a use-case call and failing fast via `.expect(...)`. Dependency direction is strictly inward: this layer depends only on `j-store-order-domain`, `j-store-common-core`, and `j-store-integration-contracts`; it never depends on infrastructure or transport details.
