# 走查

## 领域事件管道

- outbox的实现细节需要进一步完善： 
  1. 强制要求开启事务
  2. 持久化消息后，立即同步发送到消息总线
  3. 使用消息总线的事务机制确保消息可靠投递
  4. 定时扫描兜底机制可以作为补偿手段，但不应该是主要的发送途径
  5. 消息总线应该支持幂等消费，避免重复消息导致的副作用
  6. 定期归档和清理过期消息，避免 outbox 表过大影响性能

  
## 日志收集/分析

- 需要明确日志的收集和分析方案，建议使用集中式日志系统（如 ELK、Splunk）：
  1. 定义统一的日志格式，包含必要的上下文信息（如 traceId、userId、requestId）
  2. 在关键业务流程中添加足够的日志记录，尤其是异常和错误情况
  3. 配置日志级别，避免过多无用日志影响性能
  4. 定期分析日志数据，发现潜在问题和优化点
  5. 考虑使用分布式追踪系统（如 Jaeger、Zipkin）来跟踪跨服务调用链路，快速定位问题
  6. 建立日志监控和告警机制，及时发现和响应异常情况
  7. 确保日志数据的安全和隐私，避免泄露敏感信息
  8. 定期清理过期日志，避免存储压力过大
  9. 考虑使用日志分析工具进行数据可视化，帮助业务和运维团队更好地理解系统运行状况

## 鉴权SDK

1. 获取用户信息需要完整，包括用户ID、用户名、联系方式等，以便后续订单处理和客户服务。而不是单独一个 userId 字段。
