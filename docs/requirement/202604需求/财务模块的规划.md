# 财务模块（Accounting）规划

## 0. 行业调研：主流电商系统的财务模块

### 0.1 主流电商系统财务模块对比

| 平台 | 财务模块形态 | 独立性 | 核心能力 |
|------|-------------|--------|---------|
| **SAP Commerce Cloud** | 对接 SAP FI/CO（全功能 ERP 财务） | 完全独立 | 总账、应收、应付、资产会计、银行对账 |
| **Oracle Commerce Cloud** | 对接 Oracle Fusion Financials | 完全独立 | 会计中心、应付、应收、总账、固定资产、现金管理 |
| **Apache OFBiz** | 内置 accounting 组件（完整复式记账） | 独立模块 | 总账(GL)、应收(AR)、应付(AP)、发票、支付、税务、会计期间 |
| **Shopify** | 内建 Finance 套件（紧密集成） | 紧密集成 | Balance 资金账户、Capital 放贷、Tax 税务、Bill Pay 应付 |
| **Broadleaf Commerce** | Payment + Credit Account 模块 | 部分独立 | 支付处理、信用账户(B2B)、审计日志 |
| **Magento** | 核心仅发票/贷项通知单，其余靠扩展 | 扩展式 | 基础开票、税计算、第三方会计插件 |
| **PrestaShop** | 核心仅基础发票，全靠第三方模块 | 扩展式 | VAT 报表、基础开票、导出对接 |

### 0.2 关键发现

1. **独立财务模块是行业标准**：无论是 ERP 级（SAP/Oracle）还是开源级（OFBiz），财务模块都以独立限界上下文存在，而非嵌入在订单或支付模块中
2. **复式记账是核心原则**：OFBiz 遵循 OMG GL 标准，所有财务操作最终映射到总账分录（借贷必平）
3. **财务数据必须不可变**：所有主流系统的财务流水都是追加式（append-only），不允许修改或删除，仅通过冲正分录更正
4. **事件驱动是集成首选**：财务模块通过监听业务事件（订单支付、退款等）自动生成会计分录，保证业务与财务的最终一致性
5. **Money 值对象必须避免浮点**：所有系统都使用整数（分/厘）或 BigDecimal 存储金额，j-store 的 `Price(fen: Long)` 已符合此原则

### 0.3 j-store 的定位

j-store 是中等体量的多商户电商系统，不需要 SAP/Oracle 级别的全功能 ERP 财务，但需要超越 Magento/PrestaShop 的"仅开票"模式。**OFBiz 的模块划分最具参考价值**——独立 accounting 模块 + 事件驱动的总账过账，这与 j-store 的 DDD 架构天然契合。

## 1. 模块定位：与现有模块的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                        j-store 模块全景                              │
├──────────┬──────────┬───────────┬──────────┬──────────┬─────────────┤
│  shop    │  user    │  goods    │  order   │warehouse │ accounting  │
│ (商户)    │ (用户)    │ (商品+库存)│ (订单)    │ (仓储)   │ (财务)★新增  │
└────┬─────┘────┬─────┘─────┬─────┘────┬─────┘────┬─────┘──────┬──────┘
     │          │            │           │          │            │
     └──────────┴────────────┴─────┬─────┴──────────┘            │
                                  │                              │
                            ┌─────┴─────┐                  ┌────┴────┐
                            │  领域事件   │                  │ 总账过账 │
                            │ Event Bus  │◄─────────────────│ (监听)  │
                            └───────────┘                  └─────────┘
```

| 维度 | order（现有） | accounting（新增） |
|------|-------------|------------------|
| **关注点** | **订单生命周期**——"交易怎么流转" | **资金流转**——"钱怎么走、账怎么记" |
| **核心问题** | 订单状态机、退款流程、库存协调 | 应收应付、总账分录、对账结算 |
| **粒度** | 订单级行项 | 会计分录级（借贷明细） |
| **驱动方** | 用户操作驱动 | 业务事件驱动（异步过账） |
| **时间语义** | 实时（下单瞬间） | 会计期间级（日/月） |

**核心关系**：`order` 是**业务域的交易记录**，`accounting` 是**财务域的账务记录**。两者通过领域事件保持最终一致：

```
order.pay()                  → 发布 OrderPaidEvent       → accounting 生成应收分录
order.approveRefund()        → 发布 OrderRefundApprovedEvent → accounting 生成退款/红字分录
warehouse.outbound.ship()    → 发布 OutboundShippedEvent  → accounting 生成出库成本分录（V2）
order.complete()             → 发布 OrderCompletedEvent   → accounting 生成收入确认分录
```

> **关键决策**：`accounting` 是独立的限界上下文，不嵌入 `order`。订单模块只管业务流转，财务模块监听事件异步记账。符合 j-store 已有的 ACL + DomainEvent 模式。

## 4. 核心领域模型设计

### 4.1 总账子域

#### 4.1.1 会计科目（Account）

```kotlin
// ========== 聚合根 ==========
class Account(
    val accountId: AccountId,                  // 值对象
    val accountCode: String,                   // 科目编码, e.g. "1001", "2001"
    val accountName: String,                   // 科目名称, e.g. "现金", "应收账款"
    val accountType: AccountType,              // 资产/负债/权益/收入/费用
    val level: Int,                            // 科目层级 (1=一级, 2=二级, ...)
    val parentId: AccountId?,                 // 父级科目 (树形结构)
    val direction: BalanceDirection,           // 借方/贷方余额方向
    var status: AccountStatus,                // ACTIVE / INACTIVE
    val merchantCode: String? = null          // 所属商户 (null=平台级通用科目)
) {
    fun deactivate()                           // 校验：无余额、无子科目时才可停用
}

// ========== 值对象 ==========
data class AccountId(val value: String)
enum class AccountType { ASSET, LIABILITY, EQUITY, REVENUE, EXPENSE }
enum class BalanceDirection { DEBIT, CREDIT }
enum class AccountStatus { ACTIVE, INACTIVE }
```

#### 4.1.2 会计分录（JournalEntry）

```kotlin
// ========== 聚合根 ==========
class JournalEntry(
    val entryId: JournalEntryId,               // 值对象
    val entryNo: String,                        // 业务单号 "JE202604290001"
    val entryType: JournalEntryType,             // 收款/退款/结算/调整
    val sourceEventType: String,                // 来源事件类型, e.g. "OrderPaidEvent"
    val sourceEventId: String,                 // 来源事件ID, 用于追溯
    val merchantCode: String,                   // 所属商户
    val accountingDate: LocalDate,              // 会计日期（入账日期）
    val description: String,                   // 摘要说明
    val lines: MutableList<JournalEntryLine> = mutableListOf(),
    var status: JournalEntryStatus = JournalEntryStatus.DRAFT,
    val createdAt: Instant = Instant.now()
) {
    // 不变量：借贷必平
    fun addLine(line: JournalEntryLine): Result<Unit, BusinessError>
    fun post(): Result<Unit, BusinessError>               // 过账 → 不可修改
    fun reverse(reason: String): JournalEntry              // 冲正（生成红字分录）
    
    /** 校验借贷平衡 */
    fun isBalanced(): Boolean {
        val totalDebit = lines.filter { it.side == EntrySide.DEBIT }.sumOf { it.amount.fen }
        val totalCredit = lines.filter { it.side == EntrySide.CREDIT }.sumOf { it.amount.fen }
        return totalDebit == totalCredit
    }
}

// ========== 实体（JournalEntry 聚合内）==========
class JournalEntryLine(
    val lineId: JournalEntryLineId,
    val accountId: AccountId,                    // 关联科目
    val side: EntrySide,                        // 借方 / 贷方
    val amount: Price,                           // 金额（使用 j-store Price 值对象）
    val description: String? = null             // 行级摘要
)

// ========== 值对象 ==========
data class JournalEntryId(val value: String)
data class JournalEntryLineId(val value: String)
enum class JournalEntryType {
    RECEIPT,              // 收款（买家支付）
    REFUND,               // 退款
    SETTLEMENT,           // 商户结算
    COMMISSION,           // 佣金计提
    ADJUSTMENT            // 调整分录
}
enum class JournalEntryStatus { DRAFT, POSTED, REVERSED }
enum class EntrySide { DEBIT, CREDIT }
```

**分录示例——买家支付 100 元订单**：

| 行 | 科目 | 方向 | 金额 | 说明 |
|----|------|------|------|------|
| 1 | 1010 支付渠道应收 | 借 | 100.00 | 代收买家款项 |
| 2 | 6001 销售收入 | 贷 | 90.00 | 商户销售收入 |
| 3 | 3001 平台佣金收入 | 贷 | 10.00 | 平台抽佣 |

### 4.3 结算子域

```kotlin
// ========== 聚合根 ==========
class Settlement(
    val settlementId: SettlementId,
    val settlementNo: String,                   // "ST202604290001"
    val merchantCode: String,                   // 商户编码
    val period: DateRange,                      // 结算周期
    val totalOrderAmount: Price,                // 订单总金额
    val totalCommission: Price,                  // 平台佣金总额
    val totalRefundAmount: Price,               // 退款总额
    val totalRefundCommission: Price,            // 退款佣金总额（冲减）
    val settlementAmount: Price,                // 实际应结 = totalOrderAmount - totalCommission - totalRefundAmount + totalRefundCommission
    var status: SettlementStatus,               // DRAFT / CONFIRMED / PAID
    val items: MutableList<SettlementItem> = mutableListOf(),
    val createdAt: Instant = Instant.now(),
    var confirmedAt: Instant? = null,
    var paidAt: Instant? = null
) {
    fun addItem(item: SettlementItem): Result<Unit, BusinessError>
    fun calculate(): Result<Unit, BusinessError>     // 计算结算金额
    fun confirm(): Result<Unit, BusinessError>       // 确认结算单
    fun markPaid(): Result<Unit, BusinessError>       // 标记已打款

    // 不变量：settlementAmount = totalOrderAmount - totalCommission - totalRefundAmount + totalRefundCommission
}

class SettlementItem(
    val itemId: SettlementItemId,
    val orderNo: String,                        // 关联订单号
    val orderAmount: Price,                     // 订单金额
    val commissionRate: BigDecimal,              // 佣金比例
    val commission: Price,                       // 佣金金额
    val refundAmount: Price,                     // 退款金额（含该订单的退款）
    val refundCommission: Price,                 // 退款佣金
    val netAmount: Price                         // 行项应结 = orderAmount - commission - refundAmount + refundCommission
)

// ========== 值对象 ==========
data class SettlementId(val value: String)
data class SettlementItemId(val value: String)
data class DateRange(val startDate: LocalDate, val endDate: LocalDate)
enum class SettlementStatus { DRAFT, CONFIRMED, PAID }
```

## 5. 领域事件设计

### 5.1 财务模块发出的事件

```kotlin
// 总账过账完成 → 供报表查询或其他模块使用
data class JournalEntryPostedEvent(

    val entryNo: String,
    val entryType: JournalEntryType,
    val merchantCode: String,
    val totalAmount: Price,

// 结算单确认 → 通知商户可查看结算单

    val settlementNo: String,
    val merchantCode: String,
    val settlementAmount: Price,
    val period: DateRange
) : AccountingDomainEvent

// 结算打款完成 → 通知商户已打款
data class SettlementPaidEvent(
    val settlementId: SettlementId,
    val settlementNo: String,
    val merchantCode: String,
    val settlementAmount: Price,
    val paidAt: Instant
) : AccountingDomainEvent
```

### 5.2 财务模块监听的事件

```kotlin
// 来自 order: 订单支付 → 生成应收 + 总账分录
data class OrderPaidEvent(
    val orderId: OrderId,
    val paidAmount: Price,
    val items: List<OrderItemSnapshot>
)
// → 生成 JournalEntry(RECEIPT) + Receivable

// 来自 order: 退款批准 → 生成退款分录 + 冲减应收
data class OrderRefundApprovedEvent(
    val orderId: OrderId,
    val refundAmount: Price,
    val approvedItemIds: List<OrderItemId>,
    val requireReturn: Boolean
)
// → 生成 JournalEntry(REFUND) + Receivable 冲销

// 来自 order: 订单完成 → 生成收入确认分录 + 可结算
data class OrderCompletedEvent(
    val orderId: OrderId
)
// → 生成 JournalEntry(佣金计提) + 加入结算池

// 来自 order: 订单取消 → 冲销已过账分录
data class OrderCancelledEvent(
    val orderId: OrderId,
    val reason: String
)
// → 生成 JournalEntry(ADJUSTMENT) 冲销
```

### 5.3 事件流转全景

```
order ──OrderPaidEvent──────────────→ accounting (生成 应收 + 总账分录)
order ──OrderRefundApprovedEvent──→ accounting (生成 退款分录 + 冲减应收)
order ──OrderCompletedEvent───────→ accounting (佣金计提 + 加入结算池)
order ──OrderCancelledEvent───────→ accounting (冲销分录)

accounting ──SettlementConfirmedEvent──→ merchant (商户可查看结算单)
accounting ──SettlementPaidEvent────────→ merchant + order (打款完成通知)

shop ──(同步)──→ accounting (商户信息 + 佣金费率 → ShopRef)
```

## 6. 与现有模块集成方式

### 6.1 与 order 模块

| 方向 | 事件 | 效果 |
|------|------|------|
| order → accounting | `OrderPaidEvent` | 生成 `Receivable` + `JournalEntry(RECEIPT)` |
| order → accounting | `OrderRefundApprovedEvent` | 生成 `JournalEntry(REFUND)` + 冲减 `Receivable` |
| order → accounting | `OrderCompletedEvent` | 生成 `JournalEntry(COMMISSION)` + 加入结算池 |
| order → accounting | `OrderCancelledEvent` | 生成 `JournalEntry(ADJUSTMENT)` 冲销 |
| accounting → order | `SettlementPaidEvent` | 可选：订单标记已结算 |

**关键**：`order` 模块完全不知道 `accounting` 的存在。所有通信通过领域事件，符合现有 `@ApplicationModuleListener` 模式。

### 6.2 与 shop 模块

通过 `merchantCode` 关联。结算模块需要商户的佣金费率，通过 ACL 的 `ShopRef` 值对象获取。

| 方向 | 机制 | 说明 |
|------|------|------|
| shop → accounting | 事件 / 同步查询 | 获取商户佣金费率、银行账户信息 |
| accounting → shop | 事件 | 结算确认/打款通知 |

### 6.3 与 goods / warehouse 模块

**第一阶段不需要直接集成**。`accounting` 通过 `order` 的事件间接感知库存变动。  
**V2 扩展**：仓库出库时可发出成本核算事件，`accounting` 生成成本结转分录。

### 6.4 集成模式总结

| 集成 | 方向 | 机制 | Spring Modulith |
|------|------|------|-----------------|
| order → accounting | 异步事件 | `OrderPaidEvent` 等 | `@ApplicationModuleListener` |
| accounting → order | 异步事件（可选） | `SettlementPaidEvent` | `@ApplicationModuleListener` |
| shop ↔ accounting | 事件 + 同步查询 | `ShopRef` ACL | 事件用 `@ApplicationModuleListener` |
| accounting 内部 | 同步 | 总账过账服务 | 应用服务编排 |


## 8. 关键设计决策

| 决策 | 推荐 | 理由 |
|------|------|------|
| 财务是否独立模块？ | **是** | 财务是独立限界上下文，关注点与订单/商品完全不同（资金流 vs 业务流） |
| 复式记账 vs 单式记账？ | **复式记账** | 借贷必平是财务系统的基本保障，OFBiz/SAP/Oracle 均采用此模式 |
| 分录过账时机？ | **异步事件驱动** | 订单支付事件触发分录生成，保证业务流程不被财务过账阻塞 |
| 分录是否可修改？ | **不可修改，仅可冲正** | 财务审计要求，已过账分录不可变更，错误通过红字冲正分录更正 |
| 金额精度？ | **沿用 Price(fen: Long)** | 与 order 模块一致，分为单位，避免浮点误差 |
| 会计科目结构？ | **预置 + 商户可扩展** | 平台提供标准科目表，商户可在此基础上增加自定义科目 |
| 结算周期？ | **可配置（T+1 / 周 / 月）** | 不同商户可配置不同结算周期，默认 T+1 |
| 与支付渠道的关系？ | **第一阶段不直接对接** | 支付渠道对账通过对账子域（V2），第一阶段只记录渠道信息 |

## 9. 核心业务流程

### 9.1 买家支付 → 应收 + 总账过账

```
1. order.pay() → 发布 OrderPaidEvent
2. AccountingEventHandler 监听 OrderPaidEvent：
   a. 创建 Receivable（应收单）
      - orderId, buyerId, merchantCode, totalAmount
      - lines: 按行项拆分应收
   b. 创建 JournalEntry（总账分录）
      - entryType = RECEIPT
      - lines:
        借：1010 支付渠道应收    100.00
        贷：6001 销售收入         90.00
        贷：3001 平台佣金收入     10.00
   c. 校验借贷平衡 → 自动过账（POSTED）
```

### 9.2 退款批准 → 冲减应收 + 退款分录

```
1. order.approveRefund() → 发布 OrderRefundApprovedEvent
2. AccountingEventHandler 监听 OrderRefundApprovedEvent：
   a. 查找原 Receivable → 部分冲减（或全额冲减）
   b. 创建 JournalEntry（退款分录）
      - entryType = REFUND
      - lines:
        借：6001 销售收入         90.00  （红字冲减）
        借：3001 平台佣金收入     10.00  （红字冲减）
        贷：1010 支付渠道应收    100.00  （红字冲减）
```

### 9.3 商户结算 → 结算单 + 打款分录

```
1. SettlementBatchService 定时触发（或手动触发）：
   a. 按商户 + 结算周期汇总所有已完成的订单
   b. 计算每笔订单的佣金
   c. 扣减退款金额和退款佣金
   d. 生成 Settlement（结算单）
      - settlementAmount = 总订单金额 - 总佣金 - 总退款 + 总退款佣金
2. 结算单确认：
   a. Settlement.confirm() → status = CONFIRMED
   b. 发布 SettlementConfirmedEvent
3. 打款完成后：
   a. Settlement.markPaid() → status = PAID
   b. 创建 JournalEntry（结算分录）
      - lines:
        借：2101 商户应结算款     90.00
        贷：1002 银行存款          90.00
   c. 发布 SettlementPaidEvent
```

## 10. 实施建议

**最小行动路径（第一阶段）**：

1. **创建模块骨架**：`j-store-accounting` + `j-store-accounting-infrastructure` 模块结构
2. **实现总账子域**：`Account` + `JournalEntry` + `AccountingPeriod` 聚合根
3. **预置科目表**：平台级标准科目体系（10+ 核心科目）
4. **打通事件链路**：监听 `OrderPaidEvent` → 自动生成应收 + 过账分录
5. **实现结算子域**：`Settlement` + `SettlementItem`，支持按商户按周期结算
6. **单元测试**：借贷平衡校验、分录冲正、结算金额计算

**第二阶段扩展**：

7. 对账子域（支付渠道对账 + 内部对账）
8. 应付子域（供应商应付管理）
9. 财务报表（资产负债表 + 利润表）
10. 会计期间管理（月度结账）
