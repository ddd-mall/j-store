# 长期自动化维护治理需求

## 目标

j-store 需要在无人持续盯守时，能够周期性发现维护事项、形成有界变更、执行验证并提交可审查的结果，同时保证产品意图、架构边界、安全和生产数据不被 agent 擅自改变。

## 范围

- 建立跨 AI coding 工具可发现的仓库级指令入口。
- 建立维护编排、需求守护、质量门禁、安全供应链、运行事件和发布迁移六种治理能力。
- 建立由命令退出码决定的 CI、测试、规格与敏感信息门禁。
- 将本地开发配置中的明文凭据替换为环境变量。
- 明确 agent、人工审批、合并和生产操作之间的权限边界。

## 非目标

- 本次不自动修改 GitHub 仓库设置、云资源、生产环境或真实数据库账号。
- 本次不让 agent 自动合并 PR、自动发布或自动执行数据库迁移。
- 本次不引入必须付费的外部平台。
- 本次不改动业务功能和领域模型。

## 验收标准

1. 仓库根目录存在 `AGENTS.md`，明确事实来源、意图来源、验证命令、禁止操作和人工升级条件。
2. 当代码与已批准需求冲突时，治理规则必须要求报告漂移，不得用当前代码自动覆盖预期需求。
3. 六种治理 agent 均有清晰职责、输入输出、工具权限和停止条件；实现者不得担任最终批准者。
4. PR 和主分支变更能够自动执行规格测试、Gradle 测试和仓库治理检查。
5. CI 能够执行 CodeQL、依赖审查和敏感信息扫描，依赖更新由自动 PR 驱动。
6. 被版本控制的本地运行配置不得包含 PostgreSQL 密码或 JWT 私钥；示例配置只能包含非秘密占位值。
7. 文档中的 Kotlin、Java、Spring Boot 版本必须与构建配置一致。
8. 所有 agent 只能产生建议、issue、分支或 PR；合并、生产发布、生产写入、权限和密钥操作必须由人授权。
9. 交付总结必须记录执行过的检查、未执行检查、外部待办和残余风险。

## 质量目标

- **安全性**：默认最小权限；没有明文开发凭据；高风险操作必须人工批准。
- **可维护性**：治理规则具有单一权威文档，平台适配器只引用该规则。
- **可审计性**：质量判断来自可复现命令，规格变更和例外具有持久化记录。
- **可靠性**：失败任务有重试上限和停止条件，不允许无限修复循环。
