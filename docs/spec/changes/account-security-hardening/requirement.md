# 账号安全硬化需求

## 背景

当前账号实现存在跨用户越权、注册 ID 生成策略冲突、账号禁用后 Access Token 继续有效、Refresh Token 明文单槽存储和手机号未经所有权验证等问题。用户已明确要求修复这些问题。本变更以安全优先方式收敛尚未上线的账号公共契约，不保留不安全的兼容入口。

## 验收标准

1. 已认证用户只能通过 `/api/users/me` 读取或修改自己的资料，不得通过请求参数选择其他 `UserId`。
2. 消费者 API 不再暴露任意用户的启用、禁用或强制下线入口；这些应用用例仅供未来独立的平台管理身份域调用。
3. 用户注册必须携带与手机号绑定、一次性消费且未过期的验证码挑战；验证码错误、过期、重复使用或手机号不匹配时不得创建账号。
4. 注册使用应用分配的 Snowflake `UserId`，JPA 不得把非零 ID 误判为数据库生成的既有实体；真实 PostgreSQL 保存和加载必须保持同一 ID。
5. 登录失败不得区分手机号不存在与密码错误；连续失败必须受到共享存储限流，成功登录后清除该手机号的失败计数。
6. 每次登录创建独立 `sessionId`，多个设备的 Refresh Session 互不覆盖。
7. Redis 只保存 Refresh Token 的不可逆摘要，不保存可直接使用的明文令牌。
8. Refresh Token rotation 必须以原子 compare-and-set 完成；同一旧令牌并发刷新时最多一个成功，重放会撤销对应会话。
9. 修改密码、禁用账号或强制下线后，该用户的所有 Access Token 和 Refresh Token 必须立即失效。
10. 每个受保护请求必须同时验证 JWT 签名、类型、issuer、audience、key ID、会话 epoch 和服务端会话状态。
11. Access Token 与 Refresh Token 使用不同签名密钥；JWT 不携带商户角色或平台管理员权限。
12. 认证只保留 Authentication SDK 一个入口，`@SkipLogin` 与 `@RequireLogin` 的判定不得被另一套硬编码 Filter 覆盖。

## 质量目标

- 安全：默认拒绝；敏感令牌不落明文；账号和会话撤销在下一次请求立即生效。
- 并发：Refresh Token 重放和并发 rotation 不产生两个有效后继令牌。
- 隐私：跨用户查询不得返回手机号或账号状态。
- 可运维：生产环境必须显式提供 JWT 双密钥、验证码摘要密钥和短信发送适配器。
- 可验证：Controller 授权、Redis Lua、JWT claims、JPA ID 和 PostgreSQL 迁移均有对应自动化测试。

## 范围外

- 选择并签约具体短信供应商；本仓库只定义发送端口和受 `local`/`dev` profile 限制的开发适配器。
- 平台管理员账号、独立签发者和 MFA 的完整实现；消费者进程不再暴露平台账号管理 HTTP API，为该独立身份域保留应用端口。
- OAuth/OIDC、社交账号、实名认证、账号合并与注销合规流程。
