# 交付总结：原子可售库存预留

## 已交付行为

- `order.created` v3 和 `inventory.reserve` v2 携带 SPU、SKU、数量、价格与快照版本。
- 商品侧按 SPU、SKU 稳定排序，在单个事务中使用 PostgreSQL 悲观写锁校验 `ON_SALE`、商户、版本、SKU 和价格后预留库存。
- 库存与预留记录已具备 JPA 仓储、数据库迁移、乐观版本和 Boot 运行时装配。
- 商品校验或库存预留失败会产生失败事实；同一命令已完成的局部预留在事务内反向释放，无法补偿时触发整体回滚。
- 订单库存确认新增 `order.stock-confirmed` 事实；支付单只在该事实产生后创建，不再响应初始订单创建事实。
- 同步 `goods-api` 快照查询继续承担预校验，不再被视为最终销售许可。

## 验证证据

- TDD 红灯：新增测试最初因缺少 `OrderStockConfirmedEvent`、`ContractSaleItem` 和销售预留服务而编译失败。
- 商品应用测试覆盖下架、商户不匹配、SKU 缺失、版本漂移、价格漂移、库存不足补偿和成功预留。
- 真实 PostgreSQL 测试验证商品行锁持有期间下架更新被阻塞，并在预留事务提交后继续。
- 订单领域、翻译器和 Jackson 测试验证新事件、消息版本及支付时序。
- `./scripts/quality-gate.sh`：PASS；治理 13 项、spec-dev 28 项、Gradle 140 个任务全部通过。
- `spotlessApply` 与 `git diff --check`：PASS。

## 兼容性与发布

- 本项目尚未上线，`order.created` 从 v2 升至 v3，`inventory.reserve` 从 v1 升至 v2；不提供旧 Outbox 消息双读。
- 部署开发环境前应确认不存在旧版本待投递消息；必要时重建开发数据。
- 新迁移 `V20260808__sellable_inventory_reservation.sql` 只新增库存与预留表，可通过删除新增表回滚结构，但已经发生的业务预留需按订单事实处理，不能仅回滚代码。

## 残余风险

- 本变更只保证商品与库存在同一商品服务数据库中的线性化；如果未来拆成不同数据库，需要重新设计销售 Offer 一致性边界或使用可补偿 Saga。
- 商户停用与商品销售预留尚未形成跨服务原子语义，仍应作为后续独立治理项。
- 按仓库治理规则，公共契约和并发变更在合并前仍需要独立评估与人工批准；本实现没有自行批准或合并。
