# 分支管理治理需求

## 目标

j-store 需要在现有质量、安全、许可证和发布证据工作流之上，建立可执行、可审计且适合当前小型维护团队的分支管理流程，避免功能分支绕过集成分支、发布标签脱离稳定分支以及自动化直接修改受保护分支。

## 验收标准

- BMG-R1：`master` 与 `develop` 是仅有的长期分支，均禁止删除、强推和直接提交，只能通过 PR 修改。
- BMG-R2：日常短分支从 `develop` 创建并回到 `develop`；只允许小写且带类型前缀的名称。
- BMG-R3：`master` 只接收符合 SemVer 命名的 `release/v*` 和 `hotfix/v*` PR；发布或热修复完成后必须通过 `master -> develop` PR 回灌。
- BMG-R4：进入 `master` 或 `develop` 的 PR 必须通过分支方向、分支命名和 Conventional Commits 风格标题校验。
- BMG-R5：现有质量、安全、漏洞、许可证和密钥扫描同时覆盖 `master` 与 `develop`，并作为 ruleset required checks。
- BMG-R6：仓库不得配置定时依赖升级 PR。自动化只能报告可用版本；依赖升级必须由人工明确发起、逐项评估兼容性并通过 required checks。
- BMG-R7：版本标签只允许在 `master` 上人工创建；发布证据工作流不自动创建 Release、部署或迁移数据库。
- BMG-R8：流程必须提供分支创建、PR、发布、热修复、回灌、回滚、清理和远端启用的操作手册。
- BMG-R9：仓库只有一位可用审查者时不设置无法满足的审批数量，但仍要求 PR、required checks、review thread 解决和人工合并；具备独立审查者后将审批数量提升为 1。
- BMG-R10：首次将治理工作流合入尚无分支策略的 `master` 时，只允许 `codex/branch-management-bootstrap` 作为一次性 bootstrap 来源；策略落地后该例外必须自动失效。
- BMG-R11：Qodana 必须使用项目 JDK 25；PR 只报告改动文件引入的问题，任何适用的新问题都必须使质量门禁失败，既有问题不得通过提高阈值长期放行。

## 非目标

- 不在本变更中创建远端 `develop`、应用 GitHub ruleset、推送分支、合并 PR 或发布版本。
- 不引入长期 `release`、`hotfix` 或个人分支。
- 不用分支流程替代规格验收、领域评审、安全评审或发布人工批准。

## 质量目标

- **可执行性**：关键方向和命名规则由 CI 校验，不只依赖文档约定。
- **可恢复性**：发布和热修复均有明确回灌、revert 与重新发布路径。
- **最小权限**：自动化只生成候选和证据，不具备合并、发布或生产写入能力。
- **可演进性**：当前单维护者可正常工作，团队扩大后可收紧审批而不改变分支拓扑。
