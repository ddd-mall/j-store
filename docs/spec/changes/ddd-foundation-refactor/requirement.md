# DDD 基座破坏性重构需求

## 背景与目标

`j-store-common-core` 当前将聚合根、公开可变事件队列、运行时事件元数据推断和 Outbox 基础设施耦合在同一套 `framework` API 中。随着多个有界上下文接入，这些契约已经允许绕开聚合边界、提前清空待发布事件，以及把可变聚合对象序列化进事件载荷。

本次重构经确认允许破坏内部兼容性。目标是建立一套编译期安全、封装明确、框架无关的 DDD 基座，并迁移仓库内全部调用方。

## 验收标准

- DFR-R1：身份类型统一实现 `Identifier`；实体通过强类型 ID 标识。通用 ID 基类必须提供稳定的值相等与哈希语义。
- DFR-R2：聚合根统一实现 `AggregateRoot`，且聚合根标记本身不强制持有事件集合。
- DFR-R3：需要产生事件的聚合实现独立的 `RecordsDomainEvents` 契约；待发布事件集合不可由外部直接修改，聚合只能通过受保护方法记录事件。
- DFR-R4：应用层必须先获取稳定事件快照，逐条交给事务性发布者，并且仅在全部事件被接受后确认移除；发布失败时待发布事件保持不变。
- DFR-R5：基础聚合仓储只能保存和查询聚合根。非聚合实体、快照与查询模型必须使用职责明确的独立仓储接口。
- DFR-R6：每个 `DomainEvent` 在编译期直接提供稳定 envelope 元数据，不再存在运行时要求的第二层事件接口。
- DFR-R7：领域事件不得包含 `source: Any` 或聚合对象引用，只携带不可变业务数据和标量化聚合标识。
- DFR-R8：领域事件类型声明属于事件契约而非 Outbox 包；Spring 代理解析不得存在于 common-core。
- DFR-R9：消费幂等仓储使用消息/消费者中立命名；生产装配不得静默回退到无幂等实现。
- DFR-R10：Outbox 记录必须拒绝空标识、负重试次数、非法锁状态和不匹配的消息类别/投递目标。
- DFR-R11：所有现有有界上下文、序列化器、监听器、持久化转换和测试必须迁移到新契约并通过构建。

## 质量目标

- 可维护性：领域原语、消息契约和 Outbox 运行模型职责清晰，不通过兼容别名保留旧命名。
- 可靠性：事件确认协议不产生失败时静默丢失；事件 ID 在同一聚合、同一时间产生同类事件时仍保持唯一。
- 兼容性：项目尚未上线，不保留源码兼容；已持久化的事件名、版本及数据库 schema 不因本次重构改变。
- 框架隔离：domain/application 模块继续不依赖 Spring/JPA。

## 非范围

- 不改变订单、库存、支付、履约、用户和会计的业务规则。
- 不引入具体 Broker 产品。
- 不删除现有 Outbox 重试、顺序、fencing、死信与监控能力。
