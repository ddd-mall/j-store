+# 国际化币种边界修复

## 问题与影响

当前售后领域和值对象只接受 `CNY`，售后与支付 HTTP 请求也把 `CNY` 作为代码级默认值；Offer 查询与 Checkout 准备路径同样会在缺少币种事实时写入 `CNY`。因此部署 JPY、USD 等站点时必须修改核心代码，且售后请求可以自行提交币种而不是以原订单币种为准。

## 期望行为

- 核心领域只校验币种是 Java 运行时识别的 ISO 4217 三字母代码，不知道站点使用 CNY、JPY 还是 USD。
- 同一订单、交易、支付及其行项保持单一币种；支付捕获币种必须等于原支付币种。
- 售后退款币种始终从原订单金额快照派生，客户端不能覆盖。
- 部署级站点策略提供默认币种和允许币种集合；默认币种必须属于允许集合，所有配置币种必须合法。
- Payment 捕获请求未提供币种时使用当前站默认币种；显式提供的币种必须属于当前站允许集合，随后仍由支付领域校验它与原支付币种一致。
- 当前尚未把币种作为 Offer 聚合字段；在这个单站点部署模型中，Offer 查询使用当前站默认币种。一个部署内按 Offer 配置多个币种不在本次范围。

## 保持不变

- 金额继续使用现有 `Price` 的最小单位表示法，本次不改变各币种小数位和舍入语义。
- 支付、退款、售后状态机、幂等键、事件版本与持久化结构不变。
- 已显式携带正确币种的现有内部消息与 API 响应保持原字段语义。

## 验收与证据

1. CNY、JPY、USD 均可构造订单金额、支付和售后退款快照；伪造的三字母代码被拒绝。
2. 混合币种售后聚合被拒绝，售后工厂使用原订单币种并忽略客户端提供币种的可能性（请求模型中不再存在该字段）。
3. 支付捕获使用站点默认币种或显式允许币种；不允许币种在进入应用服务前返回 400；与原支付币种不一致仍由领域拒绝。
4. Offer→Checkout 使用站点默认币种，不含生产代码级 `CNY` 默认值。
5. 相关领域、应用、boot 测试通过，并用生产代码审计确认目标硬编码已清除。

## 风险与恢复

这是内部开发期的直接收敛，不保留旧售后请求 `currency` 字段的兼容适配。回滚方式是撤销本变更；不涉及数据库迁移或生产数据回填。
