# 需求：订单领域边界重构

## 目标

把订单从“交易流程总控对象”调整为“成交事实与跨域状态投影”，使支付、履约、售后和后续 Checkout 能独立演进，并消除退款批准即视为退款到账的数据完整性风险。

## 验收标准

### R1 商户与商品归属

1. 商品及其发布快照必须包含正数 `merchantId`。
2. 创建订单时，所有商品快照的 `merchantId` 必须一致。
3. 请求指定商户与商品快照商户不一致时，订单创建必须原子失败。
4. 订单、支付单、履约单和售后单必须保存相同商户标识。

### R2 成交金额

1. 订单必须保存 `currency`、`itemsSubtotal`、`discountAmount`、`shippingAmount`、`taxAmount`、`payableAmount`。
2. `payableAmount = itemsSubtotal - discountAmount + shippingAmount + taxAmount`。
3. 金额均不得为负，优惠不得超过商品小计。
4. 新订单 `paidAmount=0`、`refundedAmount=0`。
5. 订单历史金额不得因商品现价变化而改变。

### R3 支付事实投影

1. 下单后必须建立且仅建立一个对应 Payment 聚合。
2. Payment 捕获必须校验订单应付金额和币种，并按外部交易号幂等。
3. Payment 捕获成功事件到达订单后，订单才可变为 `PAID`。
4. 重复支付事实不得重复增加订单已付金额或重复发布 `OrderPaidEvent`。
5. 订单 HTTP API 不得提供直接支付操作。

### R4 履约事实投影

1. 订单记录全额支付后必须建立且仅建立一个 FulfillmentOrder。
2. FulfillmentOrder 必须保存订单、商户、收货快照和订单行项快照。
3. 只有独立履约服务可执行待发货、发货和送达操作。
4. 订单收到履约事实后更新 `FulfillmentStatus` 和行项投影。
5. 订单 HTTP API 不得提供直接备货、发货或签收操作。

### R5 售后与退款

1. 未发货售后批准后进入 `REFUND_PENDING` 并请求支付退款。
2. 已发货售后批准后进入 `RETURN_REQUIRED`，不得立即请求退款或恢复库存。
3. `RETURN_REQUIRED` 售后确认收货后进入 `REFUND_PENDING`，发布退款请求和退货收货事实。
4. Payment 退款成功后，售后进入 `COMPLETED`，订单才更新已退款金额和支付状态。
5. Payment 退款失败后，售后进入 `REFUND_FAILED`，允许再次请求同一退款，订单退款事实不得改变。
6. 财务退款分录必须由退款成功事实驱动，不得由审批事实驱动。

### R6 数据、可靠性与兼容策略

1. 所有跨域事件必须具有稳定事件名称、版本、聚合标识和发生时间。
2. 应用服务必须通过业务键或外部流水号实现幂等。
3. 聚合保存和事件发布必须继续兼容现有 Outbox/消费幂等机制。
4. 新 Flyway 迁移允许删除未上线开发库中的订单、售后相关数据并直接重建约束。
5. 领域模块不得依赖其他上下文的领域实现；跨上下文协作通过事件或消费方 ACL 完成。

## 质量目标

- 数据完整性：不允许审批成功但渠道退款失败时订单已显示退款完成。
- 可维护性：Order 不再包含支付和物流提供方行为。
- 可追溯性：支付捕获、退款和发货必须保存独立业务 ID 与外部流水。
- 原子性：非法状态或重复事实不得产生部分更新。
- 可演进性：后续 Cart、Pricing、多仓和第三方 Provider 不需要再次改变订单核心职责。
