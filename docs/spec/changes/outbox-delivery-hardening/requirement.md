# Outbox 投递闭环修复需求

## 背景与目标

当前 Transactional Outbox 已具备提交后低延迟唤醒、周期轮询、租约、fencing、顺序投递和消费幂等，但生产审查发现清理吞吐、调度失败观测、事务提交前事件确认和消费状态生命周期仍未闭环。

本变更在不改变 at-least-once 投递语义的前提下，确保投递基础设施能够持续收敛历史数据、准确暴露失效状态，并在数据库提交失败时保留可重试的聚合事件。

## 开发期变更策略

项目尚未上线，不存在需要保留的生产数据或仓库外稳定接口。用户已明确接受破坏性重构，因此本变更直接收敛当前接口、配置和数据库目标结构：不保留旧 `cleanup-cron` 配置、不提供可选清理依赖，也不为可重建开发库增加兼容迁移。该决策在本变更范围内取代 `outbox-production-hardening` R9 对新增 retention 索引的迁移要求；已有开发数据库需要清理 Flyway 历史并重建。

## 验收要求

- R1：历史 Outbox 清理必须分批执行，并在单轮预算内持续删除，不能把每次调度的吞吐限制为一个批次。
- R2：清理达到单轮预算且仍可能存在积压时，后续短周期调度必须继续推进；空队列不得忙等。
- R3：relay executor 拒绝任务必须记录为调度失败；不得把拒绝误报为成功，也不得向已经提交的业务事务传播失败。
- R4：Outbox 发布者只有在数据库事务实际提交后才能确认聚合待发布事件；事务回滚或 commit 失败必须保留原事件队列。
- R5：非事务性 `DomainEventPublisher` 保持发布成功后立即确认的默认语义，领域层不得依赖 Spring。
- R6：消费幂等明细必须具有显式、可配置且不短于 Outbox 的保留期，并通过有界批次持续清理。
- R7：只有能够从本地 Outbox 生产水位证明安全恢复的内置 local consumer 顺序游标，才可在超过保留期且对应流不存在未完成 Outbox 消息时回收；外部消费者游标不得在缺少生产水位时删除。回收后首次收到序号大于 1 的消息不得产生虚假 sequence gap，普通新消费者不得跳过序号前缀。
- R8：不得清理 DEAD_LETTER、FAILED、PENDING 或 IN_PROGRESS 消息所需的幂等/顺序状态。
- R9：配置必须拒绝非正批次、非正调度间隔、非正批次预算，以及短于 Outbox 保留期的消费保留期。
- R10：清理运行时必须强制装配消费状态保留端口，不得因缺少实现静默跳过消费状态清理。
- R11：所有使用 `SnowFlakSequence` 创建的正数领域 ID 在当前时间范围内必须保持为正，并正确保留 5-bit worker/datacenter 位布局。

## 质量目标

- 可靠性：保留现有 at-least-once、fencing 和同流顺序保证。
- 容量：默认每分钟最多执行 10 个、每个 500 行的清理批次，并在后续周期继续收敛。
- 事务安全：领域事件确认与数据库 commit 对齐。
- 可观测性：执行器拒绝进入既有 scheduler failure 指标与健康状态。

## 非范围

- 不引入 Kafka、RabbitMQ、CDC 或分布式调度器。
- 不承诺超过配置幂等保留期的任意历史消息重放去重。
- 不为长时间 listener 新增租约 heartbeat。
