# DDD 基座质量治理需求

## 背景与目标

当前主要业务上下文已经采用 DDD 四层模块，但库存不变量、店铺模块边界、领域对象封装和自动化架构门禁仍存在不一致。本次治理在不改变正常业务路径和外部 HTTP 契约的前提下，把已声明的 DDD 规则转化为可执行约束，并修复已确认的数据完整性缺口。

## 行为需求

- DQG-R1：所有已有业务实现的上下文必须使用 `domain/application/infrastructure/boot` 四模块结构；店铺上下文不得继续以混合模块承载领域与应用服务。
- DQG-R2：domain/application 模块必须保持无 Spring、Jakarta Persistence 和 Hibernate 依赖，且不得依赖自身 infrastructure/boot。
- DQG-R3：Spring 仓储适配器的写操作必须加入调用方事务，不得自行创建较窄事务；查询可以使用只读事务。
- DQG-R4：库存创建数量不得为负数；库存预留、确认扣减、释放和增加的数量必须为正数。非法数量返回 `StorageErrors.INVALID_AMOUNT`，且不得改变库存状态。
- DQG-R5：库存记录存在但对应库存聚合缺失时，应用服务必须返回业务失败，不得抛出空指针异常。
- DQG-R6：命令对象只承载数据；退款和库存预留记录的可变状态不得向聚合外暴露公共 setter。
- DQG-R7：支付与履约应用服务必须有最小回归测试，覆盖不存在资源的失败传播、幂等创建或成功变更后的保存与事件发布。
- DQG-R8：架构规则必须进入现有 governance 测试和 `quality-gate.sh`，新增上下文或依赖漂移时自动失败。
- DQG-R9：项目概览必须与店铺上下文的实际模块和实现状态一致。

## 质量目标

- 数据完整性：任意非正数库存变更都不能导致可用量或预留量反向变化。
- 可维护性：上下文模块边界由确定性测试保护，不依赖人工代码审查记忆。
- 兼容性：既有正常库存操作、商户 HTTP 路径和响应结构保持不变。
- 可验证性：先观察新增测试失败，再以最小实现使其通过，最后运行全量质量门禁。

## 非范围

- 本轮不拆分 `j-store-common-core`；其职责收敛另立变更。
- 本轮不改变 Outbox 投递、领域事件 envelope 或数据库 schema。
- 本轮不重设计事务提交后领域事件确认机制；先保留现有已发布语义并记录残余风险。
- 本轮不引入新的权限、商户角色或库存业务流程。
