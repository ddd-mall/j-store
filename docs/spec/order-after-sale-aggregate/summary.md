# 订单售后聚合拆分实施总结

## 结论

售后已从 `Order` 聚合中拆为同一订单有界上下文内的独立 `AfterSale` 聚合。项目尚未上线，因此采用直接替换：不保留旧退款 API、旧订单退款命令/事件、兼容字段或数据回填。

## 已落地能力

- 独立售后根、行项、资格/商品/履约快照及 `REQUESTED → APPROVED/REJECTED/CANCELLED` 状态机。
- 创建、审批、拒绝、撤销和申请人/商家授权查询 API；命令使用业务幂等键。
- PostgreSQL 容量账本、命令回执、悲观锁顺序、根版本校验和 Outbox 单事务写入。
- 订单只保留累计退款事实；批准事件以幂等投影更新订单，不再污染订单履约状态。
- 批准事件分别驱动财务记账和数量感知的库存恢复；需退货场景等待退货事实后再恢复库存。
- 单店商家身份由 `jstore.order.merchant-id` 配置解析，请求体不能伪造商家身份。
- 新迁移删除订单旧售后列并创建售后、容量、回执和退款事实结构。

## 验证

- 生产售后 JPA 仓储使用 embedded PostgreSQL 验证事务回滚、容量上限、部分行申请和并发竞争。
- MockMvc 验证独立售后路由、当前用户注入、幂等请求头和嵌套参数校验。
- 订单聚合、应用编排、PO 往返、库存恢复、财务监听和迁移测试通过。
- 全项目 `gradlew test --no-daemon --max-workers=1` 通过；`git diff --check` 通过。
- 生产目录旧退款命令、事件、状态、字段和路由审计无残留；历史 baseline 按“不修改既有迁移”约束保留。
