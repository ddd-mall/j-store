# 仓库版权与许可证治理需求

## 目标

j-store 需要把个人版权所有权、Apache-2.0 授权、第三方依赖合规和发布证据从一次性声明升级为可持续、可验证的仓库能力。

## 范围

- Java、Kotlin 源码及文档示例的机器可读版权声明。
- JAR、Spring Boot JAR 和源码发布包中的许可证传递。
- JVM 直接及传递依赖的许可证策略、报告和 CI 门禁。
- 原创文件与仓库内第三方文件的机器可读归属清单。
- 由人工触发标签、自动生成但不自动发布的发布证据包。
- GitHub `master`、`develop` 分支的 PR、required checks、删除和强推保护。

## 非目标

- 不自动合并 PR，不自动创建正式 GitHub Release，不部署生产环境。
- 不把第三方文件错误声明为潘少峰的原创作品。
- 不用许可证扫描替代律师对特殊、商业或不明许可证的判断。
- 不办理软件著作权登记、公证、商标或专利事务。

## 验收标准

1. 所有仓库内 Java/Kotlin 文件包含潘少峰 (Peter Pan)、2024-2026 和 `Apache-2.0` 的 SPDX 声明，Spotless 持续执行检查。
2. 所有 Gradle `Jar` 产物包含与仓库根许可证一致的 `META-INF/LICENSE`，且存在确定性验证任务。
3. 每个 JVM 子项目的直接及传递依赖均执行许可证审计；未允许、未知或元数据错误的许可证使本地门禁和 CI 失败，并留下机器可读报告。
4. 仓库存在机器可读文件归属清单；默认原创归潘少峰，Gradle Wrapper 等第三方文件以覆盖项记录原作者、来源和许可证。
5. 对人工创建并推送的版本标签，CI 生成包含源码归档、JAR、SBOM、依赖许可证报告、Git 元数据、质量日志和 SHA-256 清单的证据包，但不自动发布。
6. GitHub `master`、`develop` 只能通过 PR 修改，禁止删除和非快进推送，并要求分支策略、质量、安全、漏洞、依赖许可证和密钥扫描通过。
7. 当前候选在独立分支提交并推送；实现者不自动合并或发布。

## 质量目标

- **可审计性**：权属、许可证决策、产物内容和发布输入均有确定性证据。
- **供应链安全**：依赖升级不能静默引入未批准许可证。
- **可维护性**：策略集中配置，新增源码、依赖和第三方文件默认进入门禁。
- **最小权限**：GitHub 自动化只读源码并写入构建证明，不具备合并或发布权限。
