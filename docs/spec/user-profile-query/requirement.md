# 用户资料跨上下文查询需求

## 背景

User / Authentication 是用户身份、账号状态、昵称和已验证手机号的权威上下文。当前订单创建只从认证上下文取得 `userId`，没有读取账号资料；Shop 在单体装配中直接访问 `UserAccountRepository`，因此业务上下文无法在微服务部署时以相同方式读取用户事实。

## 目标

建立稳定的用户资料查询能力，使需要用户事实的业务上下文在模块化单体和微服务集群中使用同一消费方接口，并让新订单冻结创建时的完整买家资料。

## 验收标准

1. User 上下文必须发布不含领域聚合、密码或令牌信息的用户资料查询契约，返回用户 ID、昵称、已验证手机号和账号状态。
2. 模块化单体必须通过进程内实现读取用户资料，不经过 HTTP，也不得让消费方直接访问 `UserAccountRepository`。
3. 微服务模式必须提供受内部 Bearer 凭证保护的 HTTP 查询端点和对应客户端；未配置、缺失或错误凭证不得返回用户资料。
4. 远程客户端遇到用户不存在时必须返回空结果；网络错误、未授权、空响应、无效资料或响应用户 ID 不匹配必须作为依赖失败显式传播，不得伪装成用户不存在。
5. 创建订单时必须根据认证上下文的 `userId` 查询 ACTIVE 用户，并冻结该时刻的用户 ID、昵称和手机号；客户端不得提交或覆盖买家手机号、昵称。
6. 用户不存在或非 ACTIVE 时必须拒绝创建订单，且不得保存订单或发布订单事件。
7. Shop 创建商户或添加成员时必须通过用户资料查询契约验证账号存在，不得依赖 User 仓储或用户数据库外键。
8. Payment、Fulfillment 和 Accounting 处理既有交易时必须继续使用订单或集成消息中的交易快照，不得回查可变用户资料来解释历史交易。
9. 买家只能读取和取消自己的订单；越权请求必须使用与订单不存在相同的失败语义，公开订单响应不得暴露账号昵称或已验证手机号。

## 质量目标

- 安全与隐私：内部端点默认关闭；启用时凭证不少于 32 个字符，使用常量时间比较；验证码不得写入日志，手机号只能脱敏记录。
- 部署兼容：消费方只依赖稳定 API 契约；本地和远程适配器可通过配置替换。
- 可靠性：依赖不可用与用户不存在具有不同语义，订单不得在用户资料读取失败时降级为空快照。
- 可维护性：User 保持资料权威，Order 与 Shop 使用各自的 ACL/应用端口，不共享 User 聚合。

## 非目标

- 不建设服务发现、API Gateway、mTLS 或 OAuth2 客户端凭证基础设施。
- 不回填已有订单的空买家快照；本项目尚未上线，历史开发数据可重建。
- 不把手机号加入 JWT，也不把收货人联系方式替换为账号手机号。
